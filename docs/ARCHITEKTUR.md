# AdventureShift – Technische Architektur (Entwurf)

**Stand:** 11.10.2026  
**Produktname:** AdventureShift (`DnD2` bleibt vorerst GitHub-Repository).
**Status:** Architekturvorschlag, noch keine implementierte Architektur.

> Ziel ist ein wartbarer Multiplayer-Prototyp, der später auf einem eigenen Linux-Server betrieben wird. Bibliotheken, API-Verträge und Struktur werden im ersten Prototyp validiert; sie sind noch nicht endgültig entschieden.

## 1. Architekturprinzipien

1. **Serverautorität:** Der Server bestimmt den gültigen Spielzustand, Würfelergebnisse, Item-Übergänge und zugelassene Bewegungen.
2. **Live-Synchronisierung:** Clients erhalten Änderungen über eine dauerhafte WebSocket-Verbindung.
3. **Geheimnisse bleiben serverseitig:** Nicht sichtbare Gegner, verdeckte Bereiche und Spielleiterdaten werden unberechtigten Clients nicht übermittelt.
4. **Trennung von Darstellung und Regeln:** Grafische 3D-Würfel zeigen ein Ergebnis an, erzeugen es aber nicht verbindlich.
5. **Persistenz:** Längerfristige Daten und wichtige Ereignisse werden in PostgreSQL gespeichert.
6. **Modularer Start:** Ein klar strukturiertes Backend statt unnötig vieler verteilter Microservices.
7. **Self-Hosting:** Browser, Server und Datenbank sollen mit wenigen Diensten lokal bzw. später mit Docker Compose betrieben werden können.
8. **Genre- und Regelwerksneutralität (Produktentscheidung 11.10.2026):** Der Plattformkern darf keine festen D&D-, Fantasy- oder Kampfattributannahmen erzwingen. Cyberpunk, Steampunk, Fantasy, Sci-Fi und andere Genres sind gleichrangig.

### Trennung von Plattformkern und Regelprofilen

- **Plattformkern:** Identität, Kampagnen, Räume, Karten, Tokens, Berechtigungen, Chat/Logs, Würfelereignisse, Persistenz.
- **Konfigurierbare Vorlagen:** Charakterbogenfelder, Ressourcen (z. B. Gesundheit, Energie, Stress), Itemkategorien, Slots, NPCs/Gegner und weitere Objekttypen (z. B. Fahrzeuge, Drohnen).
- **Regelprofile:** Wahlweise rein manuelle Spielweise oder aktivierbare Module für Initiative, Bewegungskosten, Würfelmechanik, Angriffe, Effekte usw.; jedes Profil versionieren.
- **Prüfbare Serverregeln:** Browser dürfen auch bei konfigurierbaren Feldern keine fremden Werte oder Items verändern. Autorisierung, Änderungsrechte und Validierung bleiben serverseitig.
- **Keine vorschnelle Plugin-Laufzeit:** Zunächst Datenvorlagen und wohldefinierte Regel-Interfaces statt beliebig ausführbarem Nutzercode; Sicherheitsmodell für Skripting wäre ein eigenes späteres Projekt.

- **HTTP/API:** Steam-Login, Session, Kampagnenverwaltung, Charakter-/Assetverwaltung.
- **Realtime-Räume:** Bewegungen, Kartenwechsel, Tokens, Initiative, Würfel und Echtzeitereignisse.
- **Regelmodul:** Optionales, kampagnenspezifisches und versioniertes Profil für Würfel, Bewegung, Aktionen, Kampf und Effekte; generische Zugriffsrechte gelten immer.
- **Persistenzmodul:** Lädt und speichert Spielzustand; benutzt Transaktionen für konkurrierende Aktionen.

### Renderer und 3D-Würfel

Ein möglicher Aufbau ist eine PixiJS-Kartenebene mit einem separaten transparenten 3D-Canvas für Würfel. Dabei müssen Eingabeereignisse, Z-Index und Ressourcenverbrauch geprüft werden. Eine 3D-Würfelbibliothek ist austauschbar zu halten, falls die Kopplung an vorgegebene Ergebnisse nicht zuverlässig funktioniert.

## 4. Steam-Authentifizierung und Rollen

### Geplanter Login-Ablauf

1. Browser startet über die eigene Backend-Route die Steam-Anmeldung.
2. Backend leitet auf den offiziellen Steam-OpenID-Endpunkt weiter.
3. Steam bestätigt die Identität durch einen Rücksprung an das Backend.
4. Backend **validiert die OpenID-Antwort serverseitig**, einschließlich Rücksprung-/Anmeldekontext, und liest die SteamID64 aus dem bestätigten Identifikator.
5. Benutzer wird über eindeutige SteamID64 gefunden oder lokal angelegt.
6. Backend setzt eine eigene sichere Sitzung; WebSocket-Verbindungen authentifizieren sich gegen diese Sitzung.
7. Kampagnenrechte werden nach Benutzerkennung und Kampagnenmitgliedschaft geprüft.

Steam OpenID 2.0 ist nicht OpenID Connect. Ein Steam-Login verpflichtet nicht dazu, das Browserspiel über den Steam-Store zu vertreiben.

### Sicherheitsanforderungen

- Steam-Passwörter niemals entgegennehmen oder speichern.
- Sitzung mit sicherem HttpOnly-Cookie, Secure unter HTTPS und geeigneter SameSite-Einstellung.
- CSRF- und Login-State-Schutz sowie Prüfung zulässiger Redirects.
- WebSocket-Handshakes und **jede** Aktion nach Nutzer, Raum und Rolle prüfen.
- Eingaben und Formeln serverseitig validieren; Rate Limits für Login, Würfeln und Bewegung.
- Spielleiterrechte niemals durch ein Client-Flag begründen; sie stammen aus dem Backend.
- Logs datensparsam halten; Cookies/Geheimnisse nicht protokollieren.
- Geheime Daten nicht nur mit CSS/Client-Logik ausblenden.

## 5. Realtime-Nachrichten (vorläufig)

Die genauen Nachrichtentypen werden in einem gemeinsamen TypeScript-Paket definiert.

| Richtung | Event (Arbeitsname) | Inhalt |
| --- | --- | --- |
| Client → Server | join_room | Kampagnen-/Raumkennung |
| Client → Server | move_request | Token, Zielposition, Befehls-ID |
| Client → Server | roll_request | Würfeldefinition, Figur, ggf. Aktion |
| Client → Server | pickup_request | Item-Instanz und Token/Charakter |
| Client → Server | equip_request | Item-Instanz und Zielslot |
| Client → Server | end_turn | Begegnung/Zug |
| Server → Clients | token_moved | Token, neue Position, Versionsnummer |
| Server → Clients | roll_result | Wurf-ID, Würfelwerte, Modifikatoren, Gesamtergebnis |
| Server → Clients | inventory_changed | Autoritativer Inventarstatus |
| Server → Clients | turn_changed | Neue aktive Figur und zulässige Aktionen |
| Server → Clients | action_rejected | Befehls-ID und sichere Fehlermeldung |

**Wichtig:** Es werden nur diejenigen Ereignisse und Zustandsfelder übertragen, die der jeweilige Empfänger sehen darf. Server gibt verbindliche Werte aus, nicht den ungeprüften Client-Vorschlag.

### Beispiel: Bewegung

1. Client sendet „move_request“ mit seinem Token und dem Ziel.
2. Server prüft Identität, Token-Eigentum, Sicht/Regeln, Felder und ggf. Bewegungspunkte.
3. Bei Erfolg aktualisiert der Server den Raumzustand und sendet „token_moved“.
4. Bei Misserfolg erhält nur der anfragende Client „action_rejected“.
5. Bei Neustart lädt das Backend die letzte gespeicherte Position.

Wegfindung (z. B. A*) kann nach dem Prototyp ergänzt werden. Wir dürfen Client-Koordinaten nicht ohne Prüfung übernehmen.

### Beispiel: Würfel

1. Berechtigter Client sendet „roll_request“.
2. Backend entscheidet über die gültige Würfelformel und ermittelt Rohwerte aus einer geeigneten kryptografischen Zufallsquelle.
3. Backend speichert die Wurf-ID und Werte; danach sendet es ein „roll_result“-Event an die zugelassenen Clients.
4. Clients animieren passende Würfel. Das **Serverergebnis** bleibt in jeder Ansicht identisch.
5. Neu verbundene Clients können das Würfelprotokoll laden.

Ein gemeinsamer Startzeitpunkt kann die Animationen zeitlich angleichen; eine identische physikalische Simulation ist nicht zwingend nötig.

### Zugangskontrollen und Fallen – Architekturentscheidung aus dem Feature-Workshop 01.10–01.16

**Produktanforderung:** Interaktive Schlösser/Codeprüfungen/Fallen gehören **nicht allein zum Inventar**. Eine Tür, ein Tor, ein Fahrzeug, ein Terminal, ein Container oder ein anderes Szenenobjekt kann unabhängig konfigurierbare Zugangsmethoden und Fallen besitzen.

- **Szenenobjekt:** Typ, Position, Zustand und Operationen (z. B. Tür öffnen, Fahrzeug starten, Truhe öffnen). Ein Zugang kann eine einzelne Operation schützen statt zwangsläufig das gesamte Objekt.
- **Zugangskontrolle/Schloss:** erlaubte Schlüsselgegenstände, Keycards, sichere Prüfung tatsächlich eingegebener Zahl-/Textcodes, Rollen-/Objektrechte, Verriegelungs- und Wiederverriegelungsregel. **Beschlossen 01.15:** Pro Objekt boolesche Gruppen (**ODER**, **UND**) und **geordnete Sicherheitsstufen**. Hierfür ist eine strukturierte, validierbare Zugangsdefinition vorzusehen; nicht beliebig ausführbarer Programmcode. Status und bereits erfüllte Stufen müssen serverseitig kontrolliert und bei Bedarf persistent abgelegt werden.
- **Zugangsmittelzustand (01.16):** Pro Item-Vorlage/Instanz Nutzungsmodus (unbegrenzt, einmalig, n Nutzungen, zeitliche Gültigkeit oder Kombination) und dazu verbleibende Nutzungen sowie Gültigkeitsgrenzen speichern. Gemeinsame generische Item-Ladungs- und Zeitlogik nutzen; nur die **erfolgreiche, bestätigte** Authentisierung kann ggf. eine Nutzung verbrauchen. Zugangsvorgang/Verbrauch sind atomar, doppelte Clientbefehle idempotent. Entwertung/Verfall als Inventaraktion ist noch nicht spezifiziert.
- **Fehlversuche:** gemeinsam oder pro Spieler, mit eigenen Schwellenwerten und Rücksetzregeln (Zeit, Spielrunden, Erfolg, Story-Ereignis, Spielleiter); zählen nur nach validierter Anfrage; Rate-Limiting gesondert.
- **Falle/Ereignis:** unabhängig von Schlosszustand ein Auslöser, z. B. dritter falscher Code. Pro Falle einmalig oder durch Zeit/Runden/Ereignis/Spielleiter erneut scharfstellbar. Optionale eigenständige Fallen für die Karte benötigen später weitere Auslösertypen.
- **Folgen:** z. B. Alarm, Tür-/Fahrzeugsperre, Explosion als Spieleffekt, Schaden, NPC-Spawn. Konkrete Berechnungen sind abhängig vom Regelprofil, dürfen nicht hart an Fantasy- oder Kampfregeln gekoppelt sein.
- **Sicherheit:** serverseitige Berechtigungs- und Codeprüfung, Geheimnisse nur dem Spielleiter, atomare Verarbeitung paralleler Eingaben, eindeutige Befehls- und Ereigniskennungen; eine Falle darf nicht versehentlich mehrfach auslösen. Zustände und Fristen auch nach Reconnect/Neustart wiederherstellen.
- **Trennung:** Fehlversuchszähler resetten ≠ Falle erneut scharfstellen ≠ Schloss öffnen/entriegeln. Das sind verschiedene Zustände.
- **Noch nicht entschieden:** Entfernen bzw. Behalten erschöpfter Keycards, Beginn/Pausieren einer Gültigkeitsfrist, Wiederaufladen, Zeitlimit und beteiligte Spieler bei mehrstufigen Prüfungen, konkrete Zeit-/Rundensemantik und Mehrfachschwellen, Interaktions-/Fallen-Auslöser und MVP-Einführungsreihenfolge.

Die Tabellenzeilen oben sind **vorläufige Datenobjekte**, noch kein implementiertes Datenbankschema. Das genaue relationale Design wird nach Abschluss des Workshops abgestimmt.

### Karten- und Szenenmodell – Beschlüsse 02.1 bis 02.49

**Produktanforderung:** Fertige Kartenbilder werden importiert **und** Karten können innerhalb der Browseranwendung erstellt werden. **02.2:** Es gibt einen Schnellmodus und einen erweiterten Baumodus auf **demselben bearbeitbaren Szenenmodell**; konkrete Editorwerkzeuge und die Einführungsphase werden später festgelegt.

- **Asset:** hochgeladenes Bild (zunächst JPEG, PNG, WebP als mögliche Formate), mit Speicherpfad, Metadaten und nachweisbaren Nutzerrechten.
- **Szene:** veränderbarer Raum mit optionalem Maßstab/Raster und mehreren grafischen/logischen Ebenen; kann importierte Assets oder eigene Zeichendaten enthalten. **02.3 beschlossen:** Szenentyp – taktisch, Reise-/Weltkarte, Story/Atmosphäre oder freier Spieltisch – mit jeweils passenden Ansichts-/Bedieneinstellungen. Alle verwenden denselben Kampagnenkontext.
- **Raster-/Maßstabsmodell (02.4):** pro Szene wählbar **aus**, **Quadrat** oder **Hex**, mit konfigurierbarer Zellgröße, Koordinatenursprung, Maßstab und Einheit. Render-Sichtbarkeit des Rasters unabhängig von Bewegungs-Snap und von kanonischen Objektpositionen speichern. Umrechnung in Entfernungen nicht fest auf D&D oder Meter zwingen. Hexausrichtung, Distanz-/Diagonalregeln und importierte Rasterkalibrierung sind noch offen.
- **Szenenobjekt:** separate Türen, Container, Fahrzeuge, Fallen, Notizen und Tokens mit eigenen Zuständen und Berechtigungen; darf das Bild-Asset nicht destruktiv verändern.
- **Editorfunktionen (02.2 beschlossen):** Ein Schnellmodus mit Skizzen/Vektorformen und ein erweiterter Baumodus mit Tiles, Stempeln, Räumen, Wänden, Dekoration und Ebenen. Beide nutzen dasselbe Szenenobjekt; technische Umsetzung kann intern verschiedene Layer-/Objekttypen benötigen. Importierte Bilder dürfen nicht destruktiv übermalt werden. Werkzeugdetails, Undo-/Versionsmodell und MVP-Reihenfolge bleiben zu entscheiden.
- **Unterschiedliche Szenenpräsentationen (02.3):** Taktikkarte mit Tokens, Reise-/Weltkarte mit Markern, Storyansicht mit Bild/Portraits/optionalem Audio, freier Tisch zum Skizzieren. Szenentyp und Sichtbarkeit steuern, welche Werkzeuge und Assets freigegeben werden; synchronisierte Szenenwechsel ohne Verlust des persistenten Kampagnenzustands. Für Medienaufbewahrung/Lizenzen und Audio-Synchronisierung benötigen wir später gesonderte Entscheidungen.
- **Sicht- und Fog-Modell (02.5 beschlossen):** Pro Szene wählbarer manueller und dynamischer Fog-of-War-Modus. Manueller Modus speichert freigegebene/verdeckte Kartenflächen; dynamischer Modus ermittelt Sicht anhand der Figurenposition und später Sichtreichweite, Wänden/Türen, Hindernissen und Beleuchtung. Spielleiter können in beiden Modi gezielt Sichtbereiche übersteuern. Gemeinsame oder getrennte Entdeckungshistorie je Spieler und detaillierte Lichtlogik sind noch offen.
- **Erkundungserinnerung (02.6 beschlossen):** Pro Szene wählbare vollständige Wiederverdeckung oder abgedunkelte Kartenerinnerung. **Aktuelle Sicht**, **erkundete Fläche** und **manuelle Spielleiter-Übersteuerung** getrennt modellieren; Persistenz nach Reconnect/Neustart. Erkundungserinnerung berechtigt nicht zum Empfang aktueller geheimer Gegner-, Fallen- oder Objektdaten. Ob die Historie gemeinsam oder individuell gespeichert wird, ist noch offen.
- **Sichtteilung (02.7):** Pro Szene wählt der Spielleiter gemeinsame Gruppensicht/Erkundung oder individuelle Sicht/Erkundung je Spieler. Zustand und Verlauf sind dauerhaft zu speichern und je Spielerfreigabe zu filtern; Gruppenaufteilung und Wechsel zwischen Modi werden später spezifiziert.
- **Lichtmodell (02.8):** Pro Szene einfacher oder dynamischer Beleuchtungsmodus. Lichtquellen haben optional Farbe, Radius, Intensität, Richtung, Status und Referenz auf eine feste Position oder ein bewegliches Objekt (Token, Item, Fahrzeug). Schalten durch autorisierte Spieler, Spielleiter oder Ereignisse. Lichtberechnung, Fog-Masken, Sicht und Objektberechtigungen getrennt behandeln. Zeit- und Verbrauchsregeln bleiben offen.
- **Szenenhindernisse (02.9):** Wiederverwendbare logische Komponente an Wänden, Türen, Fenstern und sonstigen Objekten: Sichtblockade, Lichtblockade, Bewegungsblockade getrennt definieren. Zustände (offen, geschlossen, verriegelt, zerstört, deaktiviert) ändern das Blockadeprofil. Das universelle Zugangs-/Schloss-/Fallensystem ist wiederverwendbar; **Verriegelungszustand ≠ Durchgangs-/Sichtzustand**. Geometrie, Status und Rechte persistent und serverseitig maßgeblich; Geheimtüren nicht vorzeitig an Spieler übertragen. Kollisionsausnahmen und genaue Sichtlinien-/Lichtberechnung später definieren.
- **Mehrere Kartenbilder/Stockwerke (02.10):** Eine Szene referenziert mehrere Bild-/Karten-Instanzen mit eigenen Transformationen (Position, Drehung, Skalierung, Stapelreihenfolge), optional in getrennten Stockwerken. **Grafische Ebenen und logische Stockwerke sind separate Konzepte.** Tokens, Hindernisse, Lichtquellen, Ereignisse und Fog-/Sichtzustände brauchen die korrekte Karten-/Stockwerkszuordnung; Koordinatentransformationen dürfen Objektpositionen nicht stillschweigend zerstören. Synchronisierung, Berechtigungen und persistente Zustände unabhängig vom aktuell gewählten Stockwerk gewährleisten. Übergänge zwischen Stockwerken, parallele Perspektiven und Größenlimits bleiben offen.
- **Szenenfreigabe und Etagenentdeckung (02.11):** Entwürfe bleiben privat und werden für alle, Gruppen oder einzelne Spieler freigegeben. Ein Stockwerk kann optional erst dann im Etagenwähler erscheinen, wenn ein verknüpfter Zugang (Treppe, Aufzug, Portal) nach den Sichtregeln entdeckt wurde. Bekannte Etage, Zutrittsberechtigung, aktuelle Sicht und Freigabe von Karteninhalten bleiben getrennte Zustände; serverseitig prüfen und speichern.
- **Kartenimport (02.12):** Importer-Adapter für Bilddateien und kompatible VTT-Datensätze. Importphasen: Dateiformat sicher erkennen/validieren, lesbare Quelldaten mit unterstützten Metadaten extrahieren, Vorschau und Auswahl durch den Spielleiter, danach persistente Zuordnung zu Kartenbild, Raster, Wänden, Lichtquellen und anderen unterstützten generischen Objekten. Koordinaten/Skalierung gesondert kalibrieren, unbekannte Metadaten protokollieren ohne Geheimnisse zu leaken. Keine ausführbaren Skripte aus Fremdformaten übernehmen. Konkrete DD2VTT/UVTT-Varianten und Exportformate bleiben bis zu Kompatibilitätstests offen.
- **Interaktionsregeln und Aktion-Reaktion-System (02.13):** Gemeinsamer, regelwerksneutraler Mechanismus für typisierte **Auslöser → optionale Bedingungen → erlaubte Reaktionen** über Türen, Truhen, Terminals, Fahrzeuge, Tokens, Items, Fallen und Story-Objekte. Objektübergreifende Aktionen, mehrere Folgen und bedingte Folgeschritte sind als Anforderungen vorzusehen. Regeldefinitionen validieren und in einem **serverautoritären, begrenzten** Ausführungssystem auswerten; keine ungeprüften Nutzerskripte. Jede Aktion überprüft Berechtigungen, Referenzen und Objektzustände. Zustandsänderungen/Inventartransfers atomar bzw. konsistent, ausgelöste Folgen idempotent; Kaskaden gegen Zyklen und endlose Rekursion begrenzen. Ereignisse, Zustände und relevante Fristen persistent synchronisieren; Geheimregeln und versteckte Ereignisse nicht an unberechtigte Clients übertragen.
- **Editor-UX (02.13/02.14 beschlossen):** Zwei Ansichten für **dieselbe persistente, versionierbare Regeldefinition**: ein einfacher WENN/FALLS/DANN-Assistent und ein visueller Knoten-/Ablaufeditor für verzweigte Regeln. Beide bieten Vorlagen, lesbare Regelzusammenfassungen, validierte Objektverknüpfungen, Test-/Prüfmodus und Spielleiter-Log. Komplexe Strukturen, die der Assistent nicht vollständig editieren kann, müssen verlustfrei erhalten bleiben und dort gegebenenfalls nur lesbar bzw. eingeschränkt editierbar sein. Kein Export/Import zwischen getrennten Regelformaten beim Ansichtswechsel; gemeinsame API und serverseitige Validierung. Tests sollten in einer isolierten Vorschau ohne echte Spielzustandsänderung laufen.
- **Auslöserbibliothek (02.15):** Typisierte Ereignisse für Interaktionen, Raum-/Bewegungsereignisse, Objektzustände, Gegenstände/Inventar, Codes/Fehlversuche, Quest-/Storyereignisse, NPCs/Fahrzeuge und Spielleiteraktionen. **Zwei getrennte Zeitgrundlagen als verbindliche Produktanforderung:** (1) verstrichene Echtzeit in Sekunden/Minuten/Stunden und (2) Spielrunden bzw. Rundenereignisse. Kein implizites Umrechnen; Runden-Auslöser benötigen einen tatsächlichen Rundenzähler oder ein entsprechendes Regelmodul. Persistente Timer-/Rundenzählerzustände und eindeutige Ereignis-IDs, idempotente Ausführung, Rechte- und Geheimdatenfilter. **02.16 beschlossen:** Jeder Echtzeit- oder Rundenauslöser ist einmalig oder wiederkehrend konfigurierbar, mit erlaubten Steueraktionen Start, Pause/Fortsetzen, Reset/Neustart und Abbruch durch autorisierte Aktionen/Ereignisse. Serverautoritativer persistenter Status mindestens Regel-/Instanzbezug, Zeitbasis, Zielzeitpunkt bzw. Zielrundenzahl, Aktiv-/Pause-Zustand und eindeutige Auslösekennung. Wiederholungsereignisse unterscheiden, aber einen einzelnen Tick bei Doppelnachrichten/Reconnect idempotent behandeln. **Offen:** Semantik von Offline-Zeit, Pausierung der Kampagne, verpassten Wiederholungen und gleichzeitiger Verarbeitung.
- **Bedingungsgruppen (02.17):** Gruppen aus UND/ODER/NICHT einschließlich Verschachtelung; einheitlich von Regelassistent und Graph-Editor gelesen. Typisierte boolesche/vergleichende Bedingungen müssen serverseitig validiert werden, ohne beliebige Skriptausführung.
- **Objektgebundene Node-Ports (02.17):** Jedes platzierte Szenenobjekt (auch zunächst dekorative Objekte) besitzt eine **stabile Instanz-ID**, einen menschenlesbaren Namen, Szene-/Stockwerkszuordnung und über seinen **Objekttyp definierte Port-Fähigkeiten** (Aktionseingänge, Ereignisausgänge, optional Daten-/Zustandswerte). Die Node-Palette zeigt z. B. `Tür – Szene – Stockwerk – Nordtor` und erlaubt die Auswahl dieser konkreten Objektinstanz. Eine Node verweist auf das reale Objekt und ist **keine duplizierte Kopie**. Umbenennung ändert den Anzeigenamen, nicht die Referenz. Löschung oder fehlende Fähigkeiten führen zu sichtbaren, nicht still reparierten Referenzfehlern.
- **Graph-Verbindungen (02.17):** Persistente Kanten zwischen `sourceNodeId/sourcePortId` und `targetNodeId/targetPortId`; passende Porttypen und Befugnisse vor Speichern und Ausführung prüfen. Beispiel: `Schalter.aktiviert` → `Bedingung(Keycard UND kein Alarm)` → `Tür.entriegeln`, danach `Tür.entriegelt` → `Tür.öffnen`. Ein Aktions-Eingang führt ausschließlich nach erfolgreicher serverseitiger Berechtigungs-/Zustandsprüfung zum entsprechenden Ereignisausgang. Objekt-Ports sollen aus erweiterbaren, versionierten Vorlagen stammen; neue Modultypen dürfen zusätzliche Ports bereitstellen.
- **Graph-Ausführung und UX:** Der einfache Assistent und der visuelle Editor benutzen dasselbe Regelformat; keine Datenverluste beim Ansichtswechsel. Server steuert Ausführung, sichert konsistente Objektzustände, dedupliziert Ereignisse und begrenzt Schleifen/Kaskaden. Das Layout der Nodes und ihrer Verbindungspfade ist Editorpräsentation und vom autoritativen Spielzustand zu trennen. **02.18 beschlossen:** Verbindungen dürfen szenen- und stockwerkübergreifend **innerhalb einer Kampagne** verlaufen. **Offen:** Verhalten in inaktiven Szenen (02.19), Event- versus Datenport-Typen, Konfliktregeln und Bearbeitung unter mehreren Spielleitern.
- **Kampagnenweite Node-Verbindungen (02.18):** Ein serverseitiger Ereignisrouter löst Zielobjekte über stabile IDs mit obligatorischer Kampagnenzuordnung auf. Verbindungen über Szenen und Stockwerke hinweg sind zulässig, über Kampagnengrenzen hinweg nicht. Rechte/Zugangsbedingungen gelten auch für automatisierte Aktionseingänge. Das Auslösen darf nicht vom geöffneten Client oder der aktuell angezeigten Szene abhängig sein; **02.19 beschlossen:** Pro Regel kann für eine inaktive Zielszene sofortige Ausführung, persistentes Vormerken bis zur Aktivierung oder Verwerfen bei inaktiver Szene gewählt werden. Geheime Ziele nicht an unberechtigte Browser ausliefern; Zustandsänderungen speichern, Ereignisse deduplizieren, Zyklen begrenzen und Fehler bei gelöschten Referenzen melden. Echtzeit- und rundenbasierte Trigger unabhängig vom Zielort beibehalten.
- **Ausführungsrichtlinie bei inaktiver Szene (02.19):** Node-Regel speichert den Modus `immediate`, `defer_until_activation` oder `active_only` (konzeptionelle Bezeichnungen). Der Server führt unmittelbare Zustandsaktionen ohne sichtbaren Browser aus; vorgemerkte Aufträge erhalten stabile Ereignis-/Auftrags-IDs, Zielreferenz, Status und Aktivierungsbedingung, bleiben persistent und werden bei späterem Ausführen erneut auf Rechte, Bedingungen und gültigen Objektzustand geprüft. Bei `active_only` wird der Versuch bei inaktiver Szene verworfen, nicht verspätet nachgeholt. Deduplication/Idempotenz je Auftrag und ein nachvollziehbares Spielleiterprotokoll; Fehlziele und ungültige Bedingungen sichtbar als Fehler behandeln. Die Definition von Szenenaktivierung, Gruppenperspektiven, Ablauffristen und konkurrierenden Aufträgen ist später zu entscheiden.
- **Typisierte Node-Ports (02.20):** Portkategorien mindestens Ereignis-/Aktionstrigger, boolescher Zustand, Zahl, Text und stabile Objekt-/Figuren-/Itemreferenzen, später erweiterbar. Portmetadaten umfassen Richtung, Typ und stabile ID. Verbindungen werden beim Bearbeiten und serverseitig bei der Ausführung validiert; inkompatible Typen dürfen nicht stillschweigend vermischt werden.
- **Inverter-Node (02.20):** Eigenständiger sichtbarer, typisierter NOT-Knoten mit booleschem Eingang und booleschem Ausgang; hinter einen Ausgang oder vor einen Eingang schaltbar. Keine implizite Inversion beliebiger Event-, Text- oder Objektports. Details zu Ereignisimpulsen und Dauersignalen werden in 02.21 entschieden.
- **Signalanzeige und farbige Verbindungen (02.20):** Visuelle Leitungen und Ports anhand ihrer **Typen** farblich codieren. Verbindung vorhanden, Wert/Signal aktiv, Ereignisimpuls und Fehlerzustand als **separate Diagnose-/Präsentationsdimension** darstellen; zusätzliche Beschriftungen/Icons statt exklusiver Farbcodierung. Berechtigter Spielleiter kann beim Test den **tatsächlichen Ist-Zustand** aus dem autoritativen Servermodell sehen (inkl. fehlendem Signal), während Simulationen ohne reale Zustandsänderungen gekennzeichnet sind. Eine bestehende Kante ist nicht gleich ein aktives Signal. Signalverlauf und Werte müssen aus Serverzuständen/Ereignissen stammen, Graphlayout/Farbwahl dürfen diese nicht definieren. Debug-Daten und Geheimnisse nur berechtigten Spielleitern liefern.
- **Qualitäts-/Sicherheitsplanung (02.20):** Datentypen, Zustandsmodell, eindeutige Ereigniskennungen, Iterationen/Limits bei Event-Kaskaden, deterministische Regeln bei konkurrierenden Signalen, graphbezogene Versionierung sowie isolierte Testausführung sorgfältig spezifizieren und testen. Konkrete Farbpalette, Persistenz von kurzlebigen Impulsen und exakte Signalzeitpunkte bleiben offen.
- **Signalarten und Halteschalter (02.21):** Ereignisports übertragen **punktuelle Impulse**, Daten-/Statusports dagegen **anliegende aktuelle Werte**. Eine Schaltobjekt-Instanz erhält als Eigenschaft **Schalter** (rastender boolescher EIN/AUS-Zustand) oder **Taster** (EIN ausschließlich während gültiger Drück-/Halteaktion). Der Betätigungsimpuls ist ein eigener Ereignisport und nicht identisch mit einem anliegenden Haltezustand. Bei einem Halteschalter gilt das boolesche Ausgangssignal `true` nur solange die zugeordnete Aktion tatsächlich gültig aufrechterhalten wird; beim Loslassen wird `false` übertragen. Ein anderer Spieler kann währenddessen unabhängig eine so freigegebene Tür durchqueren. Halteaktionen benötigen serverseitig autorisierten Spieler-/Figurenbezug, Start/Ende, Schutz gegen falsche dauerhafte Aktivsignale sowie eine noch zu spezifizierende Abbruchstrategie bei Verbindungsverlust. **02.22 beschlossen:** Die angeschlossene Tür/Barriere definiert unabhängig vom Schalter-/Taster-Modus ihre Signalverlust-Reaktion: sofort zurückschalten, Stellung beibehalten oder nach separat wählbarer Echtzeit- bzw. Rundenverzögerung reagieren. Konsequenzen für Figuren im Durchgang bleiben in 02.23 offen.
- **Ist-Zustand/Simulation (02.21):** Verbindungstopologie, boolesche Ausgangszustände, zuletzt ausgelöster Ereignisimpuls und Fehlersituationen bleiben unterschiedliche Diagnosezustände. Im Live-Test nur autorisierte Serverzustände zeigen; in isolierter Simulation keine echten Objektzustände verändern. Eine Inverter-Node invertiert boolesche anliegende Werte, keine Ereignisimpulse ohne definierten Konverter. Exakte Impulsdauer, Reconnect, Kollision und gleichzeitige Halter offen.
- **Schaltquellen und Signalverlust (02.22):** Die Objektvorlage enthält passende Ports und eine konfigurierbare Betriebsart `switch` (rastend) oder `push_button` (gehalten). Der boolesche Zustand wird serverseitig autoritativ geführt; einzelne Betätigungsereignisse sind separate Ports. Zielobjekte speichern unabhängig davon eine Rückstellregel `immediate`, `retain_state` oder `delayed` samt gewählter Zeitgrundlage Echtzeit/Spielrunden. Stabile Referenzen, berechtigtes Starten/Beenden der Halteaktion, sichere Behandlung von Verbindungsabbrüchen und Synchronisierung von Mehrspielerzuständen vorsehen. Konkrete Kollisions- und Schadensfolgen bei Schließen während einer Durchquerung sind offen (02.23).
- **Blockierte Schließvorgänge (02.23):** Tür-/Barriereninstanzen besitzen eine vom Schaltertyp unabhängige Kollisionsrichtlinie `wait`, `reopen` oder `force_close` (konzeptionelle Namen). Der serverseitige Schließversuch prüft den logischen Durchgangsbereich gegen relevante Figuren/Objekte. Schließbefehl, erkannte Hindernisse, abgebrochener Vorgang, Wiederöffnung und tatsächlich abgeschlossene Schließung sind getrennte Zustände/Ereignisports; `closed` erst nach erfolgreichem Wechsel ausgeben. Parallel ablaufende Figurenbewegung und Türzustandsänderung müssen konsistent verarbeitet werden. Im Modus `force_close` keine implizite Schadens- oder Positionsänderung annehmen; regelwerksabhängige Folgen folgen erst mit 02.24. Exakte Kollisionsgeometrie, unterschiedliche Token-/Fahrzeuggrößen, Wiederholungsversuche, Mehrspielerzustände und Bewegung während der Schließung bleiben zu spezifizieren. Test-/Simulationsdaten dürfen keine echten Zustände verändern.
- **Kampagnenstandards und Objekt-Ausnahmen (02.24):** Kampagneneinrichtung enthält zentrale Standardwerte für allgemeines Objekt-/Interaktionsverhalten (z. B. Tür-Kollision aus 02.23, Folgen erzwungener Türschließung und daran geknüpfte Regelprofil-/Node-Effekte). Für neue Szenenobjekte gelten typbezogene Kampagnenstandards, sofern eine Eigenschaft nicht ausdrücklich an der Objektinstanz überschrieben wurde. In der UI effektiven Wert und Quelle (Standard vs. Instanzausnahme) zeigen. **Auflösung und Rechte serverseitig** durchführen; keine fixen D&D-Formeln im Kern, regelabhängige Schaden-/Statusberechnung nur über vorhandene Profile. Konfiguration und Ausnahmen persistent/versionierbar; **02.25 beschlossen:** Für jede Änderung eine Vorschau und explizite Auswahl, ob sie nur Neuanlagen oder auch bestehende nicht überschriebene Objektwerte betrifft. Objekt-Ausnahmen bleiben geschützt. Bei Anwendung nur auf Neuanlagen muss der alte wirksame Wert bereits bestehender Instanzen erhalten bleiben (z. B. Snapshot/versionierte Default-Bindung). Bestehende Standardwerte nur mit bewusster Auswahl ändern; Zielmenge und Auswirkungen vor Commit ermitteln. Autorisierung, nachvollziehbare Versionierung/Protokollierung und konsistentes Anwenden sind erforderlich. Verhalten aktiver Timer/Node-Ereignisse und Undo bleiben gesondert offen. Kampagnenerstellungs-Assistent wird in Hauptbereich 09 genauer gestaltet.
- **Node-Arbeitsbereiche und Untergraphen (02.26):** Eine Kampagne kann **beliebig viele benannte Node-Arbeitsbereiche** für Szenen/Funktionen/Themen haben; Arbeitsbereiche sind keine Grenzen für Signal- und Ereignisverbindungen. Nodes können in persistente, ein-/ausklappbare Gruppen und benannte Untergraphen mit explizit sichtbaren Schnittstellenports organisiert werden. Kampagnenweite Kanten zwischen Arbeitsbereichen bleiben mit stabilen Node-/Port-/Objekt-IDs verknüpft; Querverweise sind in einer such- und navigierbaren Gesamtübersicht zugänglich. **Layout-/Gruppen-/Ansichtsdaten getrennt von serverautoritärer Regellogik**, damit Verschieben, Umbenennen oder Einklappen keinen Spielzustand verändert. Mehrfach referenzierte Objekt-Nodes bleiben dieselbe Objektinstanz und werden nicht kopiert. Versions-/Referenzvalidierung, serverseitige Berechtigungs- und Geheimdatenfilter sowie Statusanzeige von Signalen gelten auch über Arbeitsbereiche hinweg. **02.27 beschlossen:** Versionierbare Untergraph-Vorlagen mit konfigurierbaren Parametern und expliziten Ein-/Ausgangs- sowie Objektbindungen; laufende Schaltungen nicht ungefragt durch Änderungen an der Vorlage ersetzen. Die genauen Schnittstellenformate bleiben zu spezifizieren.
- **Wiederverwendbare Node-Bausteine (02.27):** Persistente, benannte und versionierte Untergraph-Vorlagen mit definierten, typisierten Ein-/Ausgangsports und Parametern; konkrete Objektinstanz-IDs und Einstellungen beim Einsetzen zuordnen. Vorlagen können mehrfach instanziiert werden, ohne identische Spielzustandsinstanzen zu erzeugen; ein Update der Vorlage darf vorhandene Nutzungen nicht stillschweigend ändern. Versionen, Referenzvalidierung und bewusstes Übernehmen von Änderungen müssen vorgesehen werden.
- **Drei getrennte Node-Layoutansichten (02.27):** (1) `manual` – der Spielleiter setzt und gruppiert Nodes selbst; **handgesetzte Positionen sind verbindlich zu bewahren**. (2) `scene_auto` – automatische Anordnung nach Szenen mit **rechteckigen, mit Szenentitel beschrifteten Rahmen**, Nodes je Szene innerhalb des passenden Rahmens und sichtbaren gruppenübergreifenden Verbindungen. Nodes ohne konkrete Szenenzuordnung in einer gekennzeichneten kampagnenweiten Gruppe. (3) `global_auto` – automatische Anordnung anhand des gesamten dargestellten Graphen **ohne Szenengruppen**, mit möglichst wenigen Node-Überdeckungen, Leitungskreuzungen und unnötigen Abständen. Alle drei Modi sind nur Projektionen der **gleichen kanonischen Node-/Port-/Kanten- und Objekt-IDs**, keine Graphkopien. Mehrfach zugeordnete Nodes später gesondert spezifizieren; nicht unkontrolliert duplizieren.
- **Layoutengine und Darstellung (02.27):** Für automatische Layouts Graphlayout (ggf. hierarchisch/kräftebasiert je nach Typ), Kollision/Abstände, Szenen-Rechteckgrößen und Leiterouting als **rein editorseitige Arbeit** implementierbar; keine Ausführung des Spielgraphen bei der Layoutberechnung. **Manuelle Koordinaten niemals durch automatisches Umschalten überschreiben**; getrennte per Ansicht gespeicherte oder berechnete Layoutdaten/Zoomstände. Vollständige Kreuzungsfreiheit ist bei komplexen Graphen nicht immer erreichbar; Mindestabstände, Lesbarkeit und Layoutstabilität priorisieren. Typfarben, aktuelle Signalanzeigen, Fehlerdiagnose und Berechtigungsfilter gelten identisch in allen Ansichten. **02.28 beschlossen:** Die beiden automatischen Layouts können beim ersten Öffnen und bei relevanten Graphänderungen neu berechnet werden; Schaltflächen 'Neu anordnen' sowie 'Positionen fixieren'/Auto-Layout pausieren erlauben Eingriffe. Die manuelle Ansicht bleibt bei jedem Umschalten unverändert.
- **Auto-Layout-Aktualisierung und Fixieren (02.28):** Für die Layoutprojektionen `scene_auto` und `global_auto` automatische Erstberechnung und schonende, möglichst lokale Neupositionierung nach relevanten Graphänderungen vorsehen. Die Ansicht bietet explizites `relayout` sowie eine erkennbare Fixier-/Pause-Funktion, die die **grafische** Umordnung anhält, jedoch keine Änderungen der Graphlogik oder Ausführung unterbindet. Hinzugekommene Nodes/Verbindungen dürfen während Fixierung nicht verschwinden; sie benötigen eine nachvollziehbare Zwischenplatzierung oder eine Anzeige ausstehender Layoutänderungen. Layoutkoordinaten pro Ansicht getrennt führen und insbesondere `manual` nie durch automatische Berechnung überschreiben. Stabilität, geringe Verschiebung und ausreichende Node-/Gruppenabstände über ständiges Layout-Optimieren priorisieren. Alle drei Ansichten zeigen dieselben autoritativen Signal-/Ereignisdaten, unabhängig vom Layoutcache. Offene Implementierungsdetails: einzelne gepinnte Nodes, Debouncing, Rechenhäufigkeit, Zoom und Rendering großer Graphen. **02.29 beschlossen:** Szenenübergreifende Leitungen wahlweise als durchgehende Pfade oder als am Szenenrahmen beschriftete Ein-/Ausgangs-Übergänge anzeigen; dieselben serverseitigen Verbindungen und Signalzustände bleiben erhalten.
- **Szenenrahmen-Übergänge als rein grafische Projektion (02.29):** In `scene_auto` gibt es einen Darstellungsumschalter `direct_wires` (durchgehende farbtypisierte Verbindungen durch Szenenrahmen) / `frame_connectors` (kompakte beschriftete Ein-/Ausgangs-Anker am rechteckigen Rahmen mit Navigationsverweis zur Gegenstelle). Beide Modi projizieren **dieselben persistierten Kanten mit identischen Node-/Port-/Objekt-IDs**; Rahmen-Anker sind kein zusätzlicher tatsächlicher Event-Node und dürfen nicht im Ausführungsgraphen als neue Kante/Port persistiert werden. Typfarben, Live-Ist-Signalzustände, Impulsindikatoren, Berechtigungs-/Fehlerstatus für jede Verbindung identisch anzeigen. Übergangspunkte dürfen zur Übersicht gruppiert werden, wenn jede einzelne Kante klar identifizierbar bleibt. Umschalten darf weder Regeln ausführen noch manuelle Positionen überschreiben; nur autorisierten Spielleitern sind geheime Szenenreferenzen und Sprungziele sichtbar. **02.30 beschlossen:** Mehrfach szenenbezogene Nodes erhalten eine frei wählbare primäre Szene oder „Kampagnenweit“ als Anzeige-Heimat; andere Szenen zeigen beschriftete Referenzen/Übergänge ohne Kopie der Node/Signale. Offen bleiben Leitungsrouting, Bündelung, Standardmodus und Skalierung.
- **Primärer Anzeigeort und UI-Verweise für Mehr-Szenen-Nodes (02.30):** Eine Logik-, Bedingungs- oder Timer-Node kann für `scene_auto` einen frei wählbaren **Anzeige-Heimatort** (primäre `scene_id` oder Kennzeichnung `campaign_wide`) erhalten. Nur dort wird ihre maßgebliche Node-Grafik platziert. In weiteren referenzierenden Szenen visualisieren **beschriftete Übergangs-/Referenzanker** dieselbe bestehende Node und Kante, mit Navigation und Statushinweisen. UI-Projektionen haben keine eigene serverseitige Node-ID, kein neues Event, keinen extra Port und keinen weiteren Spielzustand. **Strikte Trennung** zwischen Anzeigeheimat, tatsächlicher Szene-/Stockwerkszuordnung der physischen Objektinstanz und kanonischer Graphdefinition; das Verändern einer Anzeigeheimat darf weder die physische Tür verschieben noch Regelreaktionen auslösen. Reale Objekt- und Node-IDs bleiben eindeutig und stabil, auch wenn ein Node mehrfach referenziert wird. Relevante Namen aktualisieren, ungültige Referenzen kennzeichnen, Berechtigungen und geheime Szenen bei jeder Darstellung filtern. Genaue Standardzuordnung und Mehrfach-/Stockwerk-Sonderfälle bleiben offen. 02.31 beschlossen: read-only Live-Signalüberwachung, serverseitiges Event-Tracing und isolierte Schritt-für-Schritt-Simulation mit Breakpoints. Testfälle folgen in 02.32.
- **Node-Live-Diagnose und Protokoll (02.31):** Typisierte Port-/Kantenwerte, Verbindungsstatus, aktuelle Aktivität, Event-Impulse, Zeit-/Rundenmarkierungen sowie Fehlerdaten als berechtigt gefilterten **read-only** Diagnosekanal bereitstellen. Ausführungs-Traces referenzieren stabile Node-/Port-/Objekt-/Kanten- und Kampagnen-IDs; Schritte enthalten Ursache, evaluierten Bedingungswert, resultierende Aktion, Erfolg/Abbruch und relevante Event-Kennung. Read-only heißt ausdrücklich, dass Beobachtung und Haltepunktanzeige niemals reale Ereignisketten oder Spielzustände stoppen bzw. ändern. Logging beschränken und sensible/verborgene Informationen nur an autorisierte SL-Sitzungen ausgeben; Retention, Sampling, Export und Belastungsgrenzen später spezifizieren.
- **Isolierter Node-Debugger mit Breakpoints (02.31):** Simulation auf **separater Zustandskopie/isoliertem Kontext** mit denselben validierten Event-/Bedingungs-/Reaktionsdefinitionen wie das autoritative Regelsystem, aber ohne echte Persistenz- und Außenwirkungen. Simulation benötigt getrennte Event-/Objektzustände und später einen kontrollierbaren Echtzeit-/Rundenzeitgeber; kein Schreiben an reale Türen, Figuren, Inventare, Timer, Sichtmasken oder Szenenfreigaben. Schrittweise Ausführung, Pause/Fortsetzen und Breakpoints nur innerhalb der Simulation, mit visualisierten Trigger-/Signalpfaden und nachvollziehbaren Wertänderungen/Fehlern. Reale Serverzustände und simulierte Werte in UX und Datenmodell klar trennen, einschließlich Untergraphen und kampagnenweiten Verbindungen. **02.32 beschlossen:** Speichbare, wiederholbare Testfälle mit Testzustand, geordneten Events, virtueller Echtzeit/Rundenfolge und Soll-Ist-Prüfungen. Automatischer Laufzeitpunkt ist offen für 02.33.
- **Testszenarien, Fixtures und Assertions (02.32):** Versionierbare gespeicherte Testfall-Definitionen, bestehend aus identifizierbarem Graph-/Vorlagenbezug, ausdrücklich isoliertem Ausgangszustand, referenzierter Node-/Objektbindung, geordneten Testereignissen (z. B. Taster-Start/Release, Figurenbewegung, Szenenaktivierung, Code), virtuellen Echtzeit-Schritten bzw. Rundenfortschritten als **unterschiedlichen Zeitachsen** sowie typisierten Assertions gegen Portzustände, Ereignisfolge, Objektzustände und nicht eingetretene Nebenwirkungen. Test-Runner verwendet dieselbe geprüfte Auswertungslogik wie die echte Runtime, führt aber alle Schreib- und Außenwirkungen ausschließlich im isolierten Simulation-Kontext aus. Soll-/Ist-Differenzen, Schritt-Trace und Node-/Portreferenzen persistiert bzw. für die SL-UI nachvollziehbar aufbereiten; Testläufe mehrfach möglich. Tests auf ungültige Objektbindungen, Endlosschleifen und zu hohe Ressourcenlast begrenzen. Zukunftsdetail: deterministische Zufallsquellen, parallele Ereignisse, Testfixture-Migration und die mit 02.33 beschlossenen konfigurierbaren Testauslöser (manuell, nach relevanten Änderungen, vor Aktivierung). Geheimnisse und Testlogs nie an unberechtigte Clients ausliefern.
- **Testausführungspolitik für Node-Schaltungen (02.33):** Pro Graph/Schaltung konfigurierbare Testauslöser `manual`, `on_relevant_change` und `before_activation` (konzeptionelle Bezeichner; kombinierbar). Änderungsabhängigkeiten über stabile Graph-/Untergraph-/Port-/Objekt-/Vorlagenreferenzen ermitteln und nur betroffene Tests in der isolierten Ausführungsumgebung starten; rein visuelles Auto-Layout, Node-Positionen und Ansichtswechsel erzeugen keinen Testbedarf. Testaufträge bei schneller Änderungsfolge begrenzt bündeln, mit Versions-ID/Snapshot des geprüften Graphen verknüpfen und technisch wie fachlich eindeutig als `passed`, `failed`, `not_run`, `stale`, `running` oder `error` zurückmelden. Alte Ergebnisse bei neuer Logikversion nicht als aktuell behandeln. Vor Freigabe Prüfstatus zeigen, aber **02.34 beschlossen:** Freigaberichtlinie pro Kampagne mit optionaler Schaltungsausnahme – Testfehler warnen oder blockieren; berechtigte Übersteuerung ausschließlich bei expliziter Erlaubnis und mit Audit-Eintrag. Stale-/fehlende Testergebnisse entsprechend behandeln; keine Übersteuerung von zwingenden Sicherheitsprüfungen. Simulation darf niemals echte Spielzustände verändern; serverseitige Berechtigungen und Ausführungsvalidierung bleiben unabhängig vom Teststatus verbindlich.
- **Testfreigaberichtlinien und Audit-Overrides (02.34):** Kampagnenregelprofil enthält einen globalen Node-Testfreigabestandard mit sichtbaren, optionalen Schaltungsausnahmen. Vor dem Aktivieren einer Regelversion validiert der Server den Teststatus **für genau die aktuelle Graph-/Vorlagenversion**: bestanden, fehlgeschlagen, fehlend, veraltet, laufend oder technisch fehlerhaft. Regelmodus `warn_only` lässt die Aktivierung trotz Teststatus zu und zeigt Warnungen; `require_current_pass` verweigert die testbezogene Freigabe ohne aktuelle erfolgreiche Pflicht-Assertions. Ein `override_allowed`-Merkmal ist gesondert festzulegen; nur autorisierte Spielleiter dürfen eine Testsperre bewusst übergehen. Jede Übersteuerung benötigt begründeten Auditdatensatz mit handelnder Identität, Zeit, Graphversion, Schaltungs-/Kampagnenbezug, Teststatus und Vorgang. Serverseitig Race-Conditions beim Test-/Freigabe-Snapshot verhindern, alte erfolgreiche Testergebnisse nie für geänderte Logik wiederverwenden. **Wichtige Unterscheidung:** Testfreigabe-/Override-Politik kann niemals Syntax-/Typ-/Referenz-/Berechtigungs-/Sicherheitsvalidierung der Event-Engine ausschalten. Testausführung verbleibt isoliert ohne echte Spielwirkungen. Konkrete globale Standardauswahl, Audit-Aufbewahrung und Details berechtigter Overrider werden später abgestimmt; 02.35 legt Konfliktstrategien für simultane Aktionen mit Kampagnenstandards und Objektausnahmen fest.
- **Simultane Node-Aktionen (02.35):** Konfliktstrategie je Kampagne mit bewussten Objektausnahmen: serverseitige Eingangsreihenfolge, Prioritäten, gegenseitige Sperre oder definierte Zusammenführung kompatibler Eingangssignale. Typed-Ports, Berechtigungen und erfolgreiche Zustandsänderungen bleiben verbindlich; Priorität umgeht keine Schutzprüfung. Für dasselbe Ziel konsistente Verarbeitung und idempotente Event-Kennungen sicherstellen. Der Debug-Trace erklärt Konfliktparteien, angewandte Regel und gewinnende, unterdrückte oder aufgeschobene Aktion; reproduzierbare Testfälle vorsehen. Zeitfenster, Tie-Breaker, Warteschlangen und **02.36 beschlossen:** Anzahl gültiger Halter pro Taster ist aus einem globalen Kampagnenstandard abzuleiten und je Taster überschreibbar; serverseitige Halterzählung und Schwellensignal erforderlich. Verbindungsabbruch folgt in 02.37.
- **Mehrfach-Halter und Kampagnenvererbung für Taster (02.36):** Kampagne legt bei Erstellung das Standard-Halteprofil für neue Taster fest: `exclusive_one` (höchstens ein gültiger Halter), `any_one` (mehrere möglich, mindestens einer genügt) oder `minimum_n` (mindestens N verschiedene gleichzeitig haltende Figuren). Jede Tasterinstanz kann die geerbte Vorgabe explizit überschreiben; effektiven Wert, Herkunft und gegebenenfalls Mindestzahl in der UI zeigen. Globale Änderungen samt Bestandsobjekten und geschützten Ausnahmen folgen 02.25. Schalter mit rastendem Zustand und gehaltene Taster bleiben getrennte Betriebsarten.
- **Autoritativer Haltezustand und Ausgang (02.36):** Halteaktionen als serverseitig validierte aktor-/figurengebundene Vorgänge mit stabiler Identität und deduplizierter Nachrichtenverarbeitung modellieren. Aktive Halter werden nach verschiedenen berechtigten Figuren gezählt, nicht nach Anzahl der Netzwerkanfragen. `holder_count`, `required_count` und `active = threshold_met` bzw. exklusive Ein-Halter-Semantik sind Grundlage für den booleschen Zustandsport sowie optionale Schwellen-/Zählereignisse. Bei Beginn/Ende einer Halteaktion atomar neu auswerten; bei Unterschreiten von N Signal EIN -> AUS senden. Das Zielobjekt reagiert gemäß eigener Signalverlust-Konfiguration (02.22). Vorhandenes Node-Konfliktprofil (02.35) für konkurrierende Aktionen beachten; Status und Halterzahl im Debugger und isolierten Mehrspieler-Tests darstellen. **02.37 beschlossen:** Bei erkanntem Verbindungsverlust global bzw. pro Taster wählbar sofort beenden oder eine begrenzte Echtzeit-Wiederverbindungsfrist einräumen; Halterzahl und Ausgang serverseitig neu berechnen. Weitere Abbruchgründe, Figurenreichweite und Bewegung werden ab 02.38 präzisiert.
- **Reconnect-Nachfrist beim gehaltenen Taster (02.37):** Kampagnenweit konfigurierbarer Standard für `release_immediately` oder `grace_period` mit **endlicher, serverseitig kontrollierter Echtzeitdauer**, je Taster ausdrücklich überschreibbar; spätere Anpassung nach 02.25. Bei detektiertem Verbindungsabbruch eine betroffene Figuren-Halteaktion entweder sofort terminieren oder in den Status `disconnect_grace` mit Deadline überführen. Während gültiger Nachfrist bleibt der Halter entsprechend dieser Policy **vorübergehend** in der Schwellenberechnung aus 02.36 enthalten, aber eindeutig als nicht verbunden gekennzeichnet. Bei Fristende atomar entfernen, `holder_count` / `IstAktiv` neu auswerten und den resultierenden Signalwechsel über den bestehenden Graphen verarbeiten. Wiederaufnahme nur nach erneuter Authentifizierung, Übereinstimmung mit der zuständigen Figur/Halteaktion und gültiger Berechtigung; keine doppelte Halterzählung bei Retry/mehreren Sitzungen. Nachfrist kann zwingende Invalidierungen (Objekt gelöscht, Rechte entzogen, Haltezustand ungültig) nicht aushebeln. Status, Deadline und Ende im berechtigten Debugger sowie in isolierten Reconnect-/Mehrspieler-Tests nachvollziehbar. **Offen:** genaue Heartbeat-/Timeout-Erkennung, standardmäßig erlaubte und maximale Frist, Neustart-/Pausierungssemantik, weitere technische Abbruchbedingungen. **02.38 beschlossen:** Bewegung, zusätzliche Figurenaktionen und Zustandswechsel sind als kampagnenweite, tasterweise überschreibbare Haltebedingungen zu validieren. Die genaue Reichweite folgt 02.39. Türreaktion nach tatsächlichem Signalabfall bleibt unabhängig nach 02.22.
- **Halten während Bewegung und anderen Figurenaktionen (02.38):** Kampagnenprofil definiert für Taster, ob Bewegung, Distanz/Erreichbarkeit, gleichzeitig ausgeführte Figurenaktionen und relevante Figurenzustände die Halteaktion weiter erlauben bzw. beenden. Einzelne Taster besitzen bewusst gesetzte Overrides; effektive Werte und Herkunft in der UI zeigen und globale Bestandsänderungen nach 02.25 behandeln. Die Eingaben werden serverautoritär gegenüber Figur, tatsächlicher Position, Berechtigung, Objekt und gegebenenfalls aktivem Regelprofil geprüft. Bei ungültig gewordener Halteaktion genau diesen Halter entfernen, `holder_count` und `IstAktiv` neu bestimmen und entsprechende typisierte Ereignis-/Statusänderungen veröffentlichen. Ziel-Türreaktion (02.22), N-Halter-Regel (02.36) und Reconnect-Nachfrist (02.37) unabhängig halten. **02.39 beschlossen:** Interaktionsreichweite und Messmodell werden als Kampagnenstandard mit Objekt-Ausnahmen konfiguriert. Die genaue Distanzberechnung, Eingabemodi und Behandlung verbotener Bewegung werden später spezifiziert. Nachvollziehbare Abbruchursachen in Live-Trace und isolierten Szenariotests darstellen; keine D&D-spezifischen Zustände voraussetzen.
- **Reichweitenprofile für Schalter/Taster (02.39):** Kampagne liefert eine Standard-Bedienreichweite und Distanzmesskonfiguration; jeweilige Objektinstanzen dürfen bewusst überschriebene Werte haben. Die Auswertung für Interaktionsstart und eine laufende Halteaktion erfolgt serverautoritär anhand der wirklichen Figuren- und Objektpositionen bzw. der erlaubten Interaktionsweise. Für das freie Kartenmodell, Quadrat-/Hexraster und Szenenmaßstäbe keine feste D&D-Zelle annehmen. Globale Änderungen und Ausnahmeschutz nach 02.25. Konkrete Formel, Maßstab, Kontakt-/Fernbedienkonvention und gegebenenfalls Sicht-/Hindernisprüfung bleiben offen.
- **Präsenzmelder und Bewegungsmelder als Szenen- und Node-Objekttypen (02.39):** Zwei getrennte, benennbare, platzierbare und serverseitig auswertbare Sensortypen mit stabiler Objekt-/Szenen-ID, unabhängigem **Erfassungsbereich** und typisierten Portvorlagen nach 02.17/02.20. Ein Präsenzmelder kann einen **dauerhaft anliegenden booleschen Präsenzzustand** (mindestens ein qualifiziertes Ziel innerhalb der Zone) plus Betreten-/Verlassen-Ereignisse ausgeben. Ein Bewegungsmelder erkennt **Positionsänderung/Bewegung innerhalb der Zone** und kann einen `motion_detected`-Ereignisimpuls ausgeben; eine stationäre Figur löst ohne tatsächliche Bewegung keinen Bewegungstreffer allein durch ihr Dasein aus. Kontinuierliche Bewegungssignale, Wiederholrate und Sensorempfindlichkeit bleiben zur Detailplanung offen.
- **Sensor-Erfassung, Sicherheit und Diagnose (02.39):** Erfassung basiert auf kanonischen Serverpositionen/-bewegungsereignissen, nicht auf visueller Clientgrafik; Sensorzone, Bedienreichweite und Sicht-/Fog-Regeln strikt trennen. Sensor-Outputs dürfen entfernte Node-Aktionen anstoßen, aber **nicht automatisch Fog-of-War, versteckte Objekte oder Identitäten an unberechtigte Spieler offenlegen**. Bei vielen Sensoren effiziente räumliche Abfragen und Zustandsänderungs-/Bewegungsereignisse vorsehen; Echtzeit-/Runden-Semantik unverändert. **02.40 beschlossen:** Frei kombinierbare, sensortypabhängige Ziel-/Tag-/Fraktions-/Merkmals- und Umwelt-/Schwellenfilter samt Kampagnenstandards und individuellen Ausnahmen. Zonen-Geometrie (02.41), Wand-/Lichtblockade, genaue Wertebereiche und Alarm-Rücksetzlogik bleiben offen. Serverautoritärer Ist-Wert, enter/exit/motion-Events und Fehlerursachen müssen im Node-Debugger und in isolierten Tests nachvollziehbar sein. Kampagnenstandards mit gezielten Sensor-Ausnahmen vorsehen, nicht alle Objekte manuell identisch konfigurieren müssen.
- **Settingabhängige Kameras/Rauchmelder und erweiterbare Sensorfamilien (Ergänzung 02.39):** Überwachungskameras und Rauchmelder als benennbare Szenenobjekte mit stabilen Objekt-IDs, typisierten Node-Ein-/Ausgängen und sensortypabhängiger Erfassungs-/Datenquelle einplanen. **Kamera:** Blickfeld/Ausrichtung, geeignetes Ziel-/Sicht-/Bewegungsereignis und ggf. Alarm- oder Aktivstatus. **Rauchmelder:** vorhandener Umwelt-/Rauch-/Gefahrenwert, Vergleich/Schwellwert sowie mögliches Ereignis und boolescher Alarmzustand. Weitere Gerätetypen (z. B. Hitze, Gas, Geräusch, Licht, Magie) sind über versionierte Sensorfähigkeits-/Portvorlagen später erweiterbar; nicht alle als schon konkret beschlossene Implementierungen ansehen. Keine vorausgesetzte Kamera-Livevideotechnik oder vollständige Rauch-/Physiksimulation; Umweltwerte müssen aus einer tatsächlich definierten Datenquelle kommen. Genre-/Kampagnenmodule steuern verfügbare Vorlagen, ohne den Event-Kern zu verzweigen.
- **Freie, typvalidierte Erkennungsfilter und Standards (02.40):** Sensor-Capability-Schema bestimmt zulässige Eingabearten und Filter: Zielklasse (Spieler, NPC, Kreatur, Fahrzeug, Objekt), Fraktion, Tags und erlaubte Merkmale für Präsenz-/Bewegungs-/Kameraerkennung; vorhandene Umweltzustände bzw. numerische Vergleiche/Schwellen für Rauch-/Gefahrensensoren. **Verschachtelte UND/ODER/NICHT-Gruppen** aus 02.17 sind auf die zugelassenen, typisierten Prädikate anwendbar. Sensorfilter dürfen keine unpassenden Vergleichsoperatoren oder nicht vorhandenen Umweltquellen ohne Fehlermeldung akzeptieren. Globale Default-Filter pro Sensortyp beim Kampagnenstart mit individuellen Sensor-Overrides und Änderungs-/Bestandsschutz nach 02.24–02.25. Server wertet anhand kanonischer Positions-/Bewegungs- und Regel-/Umweltwerte aus; Erkennung darf nicht unberechtigt Fog, Geheimnisse oder Identitäten ausgeben. Sensor-Outputs als typisierte Zustände/Events an den kampagnenweiten Graphen binden; isolierte Tests sollen Bewegung vs. Präsenz, Filtertreffer/-fehler und Rauch-/Umweltschwellen abbilden. **02.41 beschlossen:** Geometrie als Kreis, Rechteck, Sichtkegel und Polygon mit Bearbeitung im Karteneditor; global definierte, pro Sensor überschreibbare Sichtbarkeit der Sensorzone. Hindernis-/Sichtlinienregeln bleiben für 02.42 offen.
- **Sensor-Zonengeometrie und Editor (02.41):** Sensorinstanzen besitzen referenzierte, serverseitig validierte Erfassungsgeometrie mit Formtyp `circle`, `rectangle`, `cone` oder `polygon` (konzeptionelle Typnamen), geeigneten Abmessungen, Transformation/Orientierung und Karten-/Szenen-/Stockwerksbezug. Der SL zeichnet, skaliert, verschiebt, dreht und bearbeitet Polygonpunkte direkt auf der Karte. Geometrievalidierung (z. B. ungültige Polygone), getrennte Speicherkoordinaten und robuste Erfassung unabhängig vom Client-Overlay vorsehen. Sensorstandort und zugehörige Zone müssen stabil referenziert bleiben; Bewegungskopplung, Stockwerksprojektion und Hindernisfilter in späteren Schritten festlegen.
- **Sichtbarkeitsrichtlinien für Sensorzonen (02.41):** Bei der Kampagnenerstellung wird ein globales **Zonen-Darstellungs-/Freigabeprofil** für Sensorerfassungsbereiche definiert, mit explizit überschreibbarem Sichtbarkeitswert pro Sensorinstanz. Mögliche Darstellung nur für berechtigte Spielleiter oder zusätzlich für autorisierte Spieler/Gruppen; genaue feingranulare Freigaben später gestalten. Kampagnenweite Änderungen mit Vorschau/Bestandsauswahl und geschützten Overrides nach 02.25. **Unabhängige Dimensionen:** (1) Autoritative Erfassungsgeometrie und aktive Sensorlogik; (2) SL-Editor-/Debug-Overlay; (3) an Spieler auszuliefernde Zonen-/Sensordaten; (4) Sichtbarkeit des Sensorobjekts; (5) Fog-/Entdeckungssicht; (6) aktuelle Signal-/Ereigniszustände. Verborgene Sensorzonen und Metadaten vollständig serverseitig filtern, nicht lediglich im Browser ausblenden. Die Freigabe einer Zone darf keine versteckten Personen, Objekte oder Sensordaten preisgeben. Visualisierung bzw. Umschalten der SL-Overlays ändert keine Spielregeln. **02.42 beschlossen:** Hindernisse beeinflussen die Erfassung abhängig von Sensortyp und Kampagnenprofil, mit individuellen Sensor-Ausnahmen; Sichtlinienprüfung, keine Hindernisprüfung oder definierte Material-/Durchdringungsregeln. Konkrete Licht-/Dunkelheitseinflüsse folgen in 02.43.
- **Sensor-Hindernisprofile und Sichtlinien (02.42):** Eine versionierbare Sensortyp-Fähigkeit definiert, ob eine Erfassungszone **hindernisunabhängig**, anhand einer **Sichtlinie** oder mit sensortypabhängigem **Hindernis-/Material-Durchdringungsprofil** ausgewertet wird. Kampagne setzt passende globale Defaults (z. B. optische Kamera sichtlinienabhängig); einzelne Sensorinstanzen dürfen zulässige Optionen explizit überschreiben. Vererbungsänderungen mit Vorschau/Bestandsauswahl/geschützten Ausnahmen nach 02.25. Der Server referenziert Geometrie aus 02.41 sowie getrennte Sicht-/Licht-/Bewegungsblockade-Komponenten aus 02.9; nicht jeden bewegungsblockierenden Gegenstand fälschlich als sichtblockierend behandeln. Türen, Fenster und Wände liefern dynamische, für den Sensortyp relevante Occlusion-Werte. Bei Öffnung/Schließung einer Tür, geändertem Hinderniszustand, Sensor- oder Figurenbewegung betroffene Erfassungen neu auswerten; aus erfolgreichen Erkennungen typisierte Zustands-/Event-Ports erzeugen. Eigene Durchdringungsfähigkeiten nur, wenn ihr Typ/Modul sie tatsächlich unterstützt, und nie ungeprüft an Spieler freigeben. Umwelt-/Rauchsensoren nutzen gültige Umweltwerte und keine generische Figurensichtlinie; Rauch-Ausbreitung durch Öffnungen ist ein getrenntes mögliches Umweltmodul. Erfassungszone, tatsächlich detektierbare Teilfläche, SL-Debugoverlay, Spielerfreigabe und Fog-/Geheimnisschutz unabhängig speichern/filtern. In isolierter Simulation Hinderniswechsel, Sichtunterbrechung, Fenster und Sonderdurchdringung samt Gründen für Treffer/Nichttreffer testen. **02.43 beschlossen:** Sensortypabhängige Lichtbedingungen mit kampagnenweiten Defaults, gezielten Sensor-Overrides und serverseitiger Neubewertung bei Lichtänderung. Offen bleiben genaue Schwellen, IR-/Wärme-/Spezialoptikmodelle sowie Details zu Materialeigenschaften, Stockwerksübergängen, Abfrageeffizienz und Umweltphysik.
- **Sensortypabhängige Licht- und Dunkelheitsprüfung (02.43):** Versionierte Sensorfähigkeiten und pro Sensortyp konfigurierbare Kampagnenstandards vorsehen, mit ausdrücklichen Sensorinstanz-Ausnahmen und Vererbungs-/Bestandsänderungsregeln aus 02.25. Normale optische Kameras können einen ausreichenden serverautoritativen Lichtwert voraussetzen; Nachtsichtprofile unterstützen nur die im Sensor-/Regelmodul vorgesehenen Schwachlicht- oder anderen optischen Fähigkeiten; Wärmebildsensoren prüfen valide Wärme-/Temperaturdaten statt normaler Beleuchtung. Bewegungs-, Präsenz-, Rauch- und magische Sensoren verwenden ihre jeweilige definierte Erkennungstechnik und dazu passende Licht- oder Umweltabhängigkeit. **Keine automatische Generierung zusätzlicher Sensorfähigkeiten** aus einer Einstellung und keine vorausgesetzte vollständige Wärmephysik. Licht-/Dunkelheitsbedingungen aus kanonischen Szenenlichtquellen und den getrennten Licht-/Sichtblockade-Komponenten (02.6/02.9) beziehen und bei Lichtzustands-, Sensor- oder Zieländerungen betroffene Erfassungen neu evaluieren. Bei der Erkennung Erfassungsgeometrie (02.41), Sensortyp-Filter (02.40), Hindernisprüfung (02.42), Lichtbedingungen (02.43) und Sichtbarkeitsfreigaben unabhängig beachten; Nachtsicht hebt keine Wandblockade auf. Erfolgreiche Treffer und Gründe für unterdrückte Treffer in typisierten Node-Outputs und berechtigt gefilterten Traces bereitstellen. Isolierte Tests für Hell/Dunkel, Nachtsicht und vorhandene/nicht vorhandene Wärmequelle, ohne echte Spieländerungen. **02.44 beschlossen:** Sensortypabhängig definierte Auslöse-/Nachlaufzeit, wiederholte Ereignisimpulse und gespeicherte quittierbare Alarme mit Kampagnenstandards und Ausnahmen. Echtzeit und Spielrunden bleiben getrennt. Quittierungsrechte und Resetwege folgen in 02.45; konkrete Lichtskala und Performancelimits bleiben offen.
- **Sensor-Zeitverhalten, wiederholte Events und latched alarms (02.44):** Sensortyp-Fähigkeiten bestimmen zulässige Varianten der Signalverarbeitung: sofortige Auslösung, Ansprechverzögerung bis zur Bestätigung einer Roh-Erkennungsbedingung, dauerhaft anliegender boolescher Ausgang, Ausschalt-/Nachlaufzeit, wiederholte Event-Impulse mit begrenztem Intervall sowie gespeicherter Alarmzustand, der bis zu einem gültigen Quittierungs-/Reset-Ereignis erhalten bleibt. **Unabhängige Zustandsdimensionen** für Rohdetektion, laufende Verzögerung, nachgehaltenen Ausgang, Eventimpuls und Alarm-Latch modellieren, damit ein verlorenes Ziel nicht automatisch jeden quittierpflichtigen Alarm zurücksetzt. Voreinstellungen je Sensortyp werden bei Kampagnenerstellung gesetzt, mit ausdrücklich erkennbaren Sensorinstanz-Overrides und Bestands-/Vorschauregeln nach 02.25; nur die vom Typ unterstützten Aktionen/Ports zulassen. Sensor-Timer können serverseitig entweder auf **Echtzeit** oder auf **Spielrunden** basieren (02.15/02.16), ohne heimliche Zeitumrechnung. Auslöse-/Ablauf-/Neubewertungsereignisse in der autoritativen Runtime deduplizieren und bei Überlagerung einer neuen Erkennung sowie bei gleichzeitigen Signalen konsistent gemäß 02.35 verarbeiten; endlose Impulsfolgen und Ressourcenlast begrenzen. Berechtigter Live-Debugger und isolierter Test-Runner stellen Status, verbleibende Zeit/Runden, Wiederholungen und Alarmquittierungen mit Ursachen dar; Sandbox niemals in realen Kampagnenzustand schreiben. **02.45 beschlossen:** Kampagnenstandard mit Sensor-Ausnahmen für befugte Rollen/Akteure und Quittierungsquellen (SL, autorisierte Bedienobjekte und geprüfte Node-/Szenen-Signale), mit serverseitiger Rechteprüfung und Audit. **02.46 offen:** Quittierung/Reset bei weiterhin erkannter Gefahr sowie Neustart-/Pauseverhalten, Entprellung, Retention und Skalierung.
- **Alarmquittierungsrechte und Resetkanäle (02.45):** Je Kampagne eine standardmäßige rollen-/akteursbasierte Autorisierung für gespeicherte Sensoralarme und erlaubte Rücksetzwege vorsehen; einzelne Sensorobjekte dürfen explizit abweichende Quittierungsrichtlinien erhalten. Änderungen an Kampagnen-Defaults nach 02.25. Resetanforderungen stammen entweder aus (1) einer autorisierten Spielleiteraktion, (2) einem servervalidierten Bedienelement wie Alarmterminal/Taster mit Figur-, Rollen-, Objekt- und Interaktionsrechten oder (3) einer ausdrücklich als Resetquelle freigegebenen, **vertrauenswürdigen Node-/Szenen-Automation**, deren Herkunft und Autorisierung nachweisbar ist. **Ein eingehender Node-Impuls allein ist kein Freibrief**, um Sicherheits-, Schloss-, Rollen- oder Sensorrichtlinien zu umgehen. Alle Pfade führen durch denselben serverseitigen Reset-Validierer und eine atomare Alarmzustandsänderung mit idempotenter Ereigniskennung; konkurrierende Alarmauslösungen und Resets konsistent nach 02.35 behandeln. Autorisierte/Ablehnungen mit Zeit bzw. Runde, Sensor- und Kampagnenreferenz, Akteur bzw. geprüfter Automationsquelle, Resetweg, Vor-/Nachzustand und Ablehnungsgrund auditierbar protokollieren; Aufbewahrungs-/Datenschutzgrenzen später. Berechtigte Live-Diagnose und isolierte Tests sollen Sensorreset über alle Kanäle nachvollziehen, ohne reale Alarmzustände zu verändern. Resetrecht, Sichtbarkeit des Sensors, Sichtbarkeit der Zone (02.41), Fog-of-War und Leserechte der Protokolle unabhängig modellieren. Quittierung/Reset **ändert nicht automatisch den realen Gefahreneingang**; **02.46 beschlossen:** Quittierung, Stummschaltung und Reset sind unabhängige, einzeln autorisierte Übergänge; aktive Gefahren bleiben auch nach Quittierung sichtbar.
- **Quittieren, Stummschalten und Reset als getrennte Alarmzustände (02.46):** Rohdetektion bzw. Gefahreneingang, Quittierungsstatus, Stummstatus und gespeicherten Alarmlatch unabhängig führen. Globale Sensortyp-Richtlinien bei Kampagnenerstellung mit markierten Sensorinstanz-Ausnahmen und Vererbungsregeln aus 02.25. Ein Reset kann entsprechend der freigegebenen Policy erst nach Entwarnung, unter fortbestehender Warnanzeige trotz aktiver Gefahr oder nach zusätzlicher Freigabebedingung zulässig sein; keine Resetaktion darf den tatsächlichen Sensoreingang fälschen. Quittieren, Stummschalten und Reset besitzen jeweils eigene serverseitige Berechtigungen/Quellen nach 02.45 sowie nachvollziehbare Auditeinträge. Konkurrierende Ereignisse nach 02.35 und idempotente Statusübergänge berücksichtigen; verbergen von Meldungen nur gemäß Sichtrechten. Debugger und isolierter Test-Runner müssen gültige und abgelehnte Statuswechsel bei laufender Gefahr zeigen. **02.47 beschlossen:** Wiederbenachrichtigung bei neuen Ereignissen, erneutem Grenzwertübertritt, höheren Gefahrenstufen oder Fristablauf nach Sensortyp konfigurierbar. Entprellung und Sperrfristen begrenzen Meldungsfolgen. **02.48 offen:** Empfänger und In-Game-Kanäle.
- **Wiederalarmierung und Eskalation nach Quittierung (02.47):** Regel je Sensortyp mit globalen Kampagnen-Defaults und Sensorinstanz-Overrides (02.25): Ereignis eines neuen geeigneten Ziels, erneuter Schwellwertübertritt nach Unterschreitung, gültiger Anstieg einer Gefahren-/Alarmstufe oder Ende einer Stumm-/Sperrfrist dürfen jeweils als gesonderte Auslöser für erneute Alarmmeldungen definiert werden; alternativ bis Reset keine neue Benachrichtigung. Vorhandene Detektion ist von einem **neuen** Ereignis zu unterscheiden; Dauerwerte und doppelte Netzwerkpakete nicht bei jedem Tick als neue Alarme zählen. Serverseitig stabile Ereignisidentitäten, Entprellung, Mindestabstand, Frequenzgrenzen und eindeutige Eskalationsursache anwenden. Wiederbenachrichtigung darf Stummschaltung nur gemäß expliziter Richtlinie durchbrechen; Echzeit- oder Rundenfristen getrennt führen (02.15/02.16). Rohgefahr, quittiert, stumm, gespeicherter Alarm und neuer Re-Alarm-Impuls bleiben getrennte Zustände (02.44–02.46). Berechtigte Logs und isolierte Simulation dokumentieren ausgelöste/unterdrückte Meldungen, zweite Ziele, Schwellen- und Stufenwechsel sowie Fristablauf. Keine Änderung der Rechte-/Fog-Freigabe durch Alarm-Eskalation. **02.48 beschlossen:** Empfangs-/Wirkungsregeln liegen in einer gesonderten Alarm-Node mit lokalem, szenenweitem oder kampagnenweitem Wirkungsbereich, Ziel-/Fraktions-/Tagfiltern und passenden Ausgabekanälen. Sensoren liefern nur typisierte Signale. Geräuschsensoren als zusätzliche Quell-Nodes geplant.
- **Alarm-Node, Fan-out und Wirkungsziele (02.48):** Sensoren oder andere Trigger-Nodes erzeugen typisierte Ports/Ereignisse; eine **eigenständige Alarm-Node** nimmt kompatible Alarmsignale entgegen. Eine Quelle darf mehrere beliebige Reaktions-Nodes ansteuern: beispielsweise **Bewegungsmelder -> Licht-Node, Alarm-Node, Meldungs-Node und Tür-Node**, jeweils unter den bestehenden Typ-/Rechte-/Türzustandsregeln. Die Alarm-Node modelliert räumliche Wirkung **lokal/regional**, **szenenweit** oder **kampagnenweit** und filtert Empfänger/Zielaktionen nach unterstützten Typen (alle, Freund/Feind mit eindeutigem Bezug, Tiere, NPCs, Spieler, Fraktion, Tags und kompatible Bedingungen). Ausgabe über In-Game-Sirene/Geräusch, Berechtigten-Hinweis, Terminal, geeignete NPC-/Figurenreaktion oder weitere typisierte Node-Ausgänge. **Physikalisch hörbare Wirkung, UI-Nachricht und Zielaktionsrecht sind unterschiedliche Prüfungen.** Alarm-Wirkungsregion ist nicht automatisch der Sensor-Erfassungsbereich. Serverseitiges Fan-out, Deduplikation, Schleifenschutz und Ereignis-Trace umsetzen; keine Geheimnisse an unberechtigte Clients ausliefern.
- **Geräusch-/Sound-Sensoren als zusätzliche Sensorfamilie (02.48):** Sensorobjekte können auf passende, ausdrücklich modellierte akustische Spielwelt-Ereignisse reagieren und daraus typisierte Node-Signale bilden. Datenquelle ist nicht automatisch ein Spieler-Mikrofon, Voicechat oder reale Tonaufnahme. **02.49 beschlossen:** Kombinierbare typisierte Geräuschquellen aus Spielaktionen, Objekten, Sound-/Alarm-Nodes und SL-/Szenenevents mit Quell-, Typ-/Tag- und Intensitätsmetadaten. Globale Schall-Visualisierungsrichtlinie mit Quell-/Objekt- und räumlichen Ausnahmen; tutorial-/zeit-/ereignisabhängiges Anzeigen und Verbergen. Physische/regelbasierte Schallausbreitung und Dämpfung folgen in 02.50. Geräteregeln bleiben genre- und settingneutral erweiterbar.
- **Konzeptstand globaler Kampagnenoptionen (Workshop-Vorgabe, 02.48):** Sämtliche bislang beschlossenen Kampagnenstandards und Objektausnahmen als **Anforderungen** erhalten. Aber die konkrete UI-Führung durch globale Einstellungen, die Struktur des Kampagnenassistenten und insbesondere **welche gesamten Funktionsbereiche kampagnenweit deaktiviert werden können**, werden **erst nach Planung sämtlicher Featurebereiche** entworfen und beschlossen. Keine vorzeitige Festlegung auf Menüs, Schritte oder an-/abschaltbare Module.
- **Akustische Spielwelt-Ereignisse als Node-Daten (02.49):** Kanonische Sound-/Geräuschereignisse können aus validierten Figurenaktionen, Weltobjektreaktionen, passenden Sound-/Alarm-Nodes und ausdrücklichen SL-/Szenenevents entstehen. Geeignete Daten sind stabile Event-/Quell-/Szenen-ID, räumlicher Bezug, Geräuschtyp/Tags, gegebenenfalls Intensität, Dauer und Echtzeit- bzw. Rundenzuordnung; Regeln zur konkreten Skala später. Geräuschsensoren verwenden typisierte Eingänge und Capability-Filter, die Geräusche erkennen und standardisierte Zustands-/Event-Ports an weitere Nodes geben (02.48). Server autorisiert Quellen, dedupliziert Eingaben und schützt vor selbstverstärkendem Sound -> Sensor -> Alarm -> Sound-Ereignisloop. Kein automatisches Abhören von Spielermikrofonen oder Voicechat und keine zwingende Audiodatei als Datenquelle.
- **Visualisierung von Geräuschwellen/Hörbereichen (02.49):** **Eigene Präsentations-/Sichtbarkeits-Policy**, ausdrücklich unabhängig von Erzeugung, tatsächlicher Hörbarkeit, Sound-Ausbreitung, Geräuschsensorik und NPC-/Alarm-Node-Reaktionen. Bei Kampagnenerstellung Standard für die Spieleranzeige von Wellen/Radien/Geräuschmarkierungen festlegbar. Overrides sowohl für **einzelne Geräuschquellen/Ereignisse** als auch für **definierte Szenen-/Kartenregionen** unterstützen; Regeln müssen für das aktuelle Ereignis und den relevanten Sichtbereich evaluiert und bei Überlappung später eindeutig priorisiert werden. Der Sichtbarkeitswert darf **ereignis-/zeit-/rundenabhängig** über SL-Aktion, Tutorial-Fortschritt, Szenenwechsel oder berechtigten Node-Trigger wechseln. Beispiel: Für ein Einführungsrätsel Schallwellen sichtbar, nach abgeschlossener Tutorialphase nicht mehr sichtbar, während akustische Erkennung fortbesteht. Eigene SL-Debug-/Editor-Overlays von der für Spieler serverseitig freigegebenen Visualisierung trennen. Die Visualisierung darf keine geheimen Verursacher, Positionen oder Ereignisse an nicht autorisierte Spieler verraten; Metadaten serverseitig filtern, nicht nur Client-Elemente ausblenden. Globale Defaults, Objektausnahmen und spätere Änderungen mit Vorschau gemäß 02.24–02.25. Konkrete regionale Regelpräzedenz und Schallausbreitungsgeometrie bleiben offen.
- **Workshop-Grenze bleibt bestehen (02.48/02.49):** Hier sind ausschließlich die fachlich benötigten globalen Vorgaben und Ausnahmen notiert. **Konkrete Bedienführung, Menüstruktur, Priorisierung von Einstellungen und global vollständig deaktivierbare Funktionsbereiche** erst nach Planung aller Featurethemen ausarbeiten. Nicht verwechseln mit der bereits beschlossenen Option, eine **rein visuelle** Schallanzeige ein-/auszuschalten; das ist keine Deaktivierung der Geräuschmechanik. Akustische Ausbreitung und Dämpfung werden in 02.50 spezifiziert.
- **Serverseitiger Geheimnisschutz:** Sicht auf Kartenfläche und Autorisierung für Objektdaten sind getrennt. Verborgene NPCs, Fallen, Geheimtüren, SL-Notizen oder andere sensitive Daten niemals allein durch verdeckende Client-Grafik schützen; serverseitig je Teilnehmer filtern. Persistenz/Neuverbindung und effiziente Synchronisierung der Sichtmasken einplanen.
- **Speicherung/Sicherheit:** persistente Editoroperationen, Versionen/ggf. Undo, Sichtbarkeit und Rechte serverseitig; Bild-Uploads sicher prüfen und begrenzen. Nicht freigegebene Spielleiter-Layer werden Spielerclients nicht übermittelt.

### Fachliche Trennung

- **Konfigurierbare Charakterwerte** bleiben unabhängig von optionalen **regelbasiert abgeleiteten Werten**.
- **Item-Vorlage** ist nicht dasselbe wie **konkrete Item-Instanz**.
- **Benutzerrolle** ist kampagnenbezogen, nicht global.
- **Sichtbarer Raumzustand** ist eine berechtigungsgesteuerte Sicht auf den internen Spielzustand.
- **Würfelanimation** ist nicht die Quelle des Würfelergebnisses.

## 8. Self-Hosting und Betrieb

### Ein-Server-Ausbau zu Beginn

- Caddy nimmt HTTPS-Verbindungen entgegen und stellt das Web-Frontend bereit bzw. leitet an die Dienste weiter.
- Der Node.js-Server stellt API und WebSocket-Räume bereit.
- PostgreSQL wird nicht direkt ins Internet veröffentlicht.
- Karten und Token-Dateien liegen auf einem persistenten Volume (später ggf. objektbasiert).
- Docker Compose beschreibt Dienste, Netzwerke, Volumes und Umgebungsvariablen.
- Eigene Domain, TLS-Zertifikate, Firewall, Backup und Monitoring sind einzuplanen.

### Betriebsanforderungen

- Keine Schlüssel oder Zugangsdaten im Git-Repository.
- Konfiguration aus Umgebungsvariablen/Secrets; eine Beispielkonfiguration darf keine echten Secrets enthalten.
- Regelmäßige Backups **von Datenbank und Dateien**; Wiederherstellung testen.
- Versionierte DB-Migrationen, Health-Check, Log-Rotation und Updates.
- Vor Produktivbetrieb Sicherheitstests, insbesondere für Rollen, geheime Daten und Datei-Uploads.

**Noch nicht bestimmbar:** CPU/RAM-Bedarf und Zahl möglicher paralleler Räume. Diese Werte hängen von Bibliotheken, Kartengröße, Animationsaufwand und Nutzerzahl ab und müssen gemessen werden.

## 9. Tests, die wir früh durchführen müssen

1. Zwei bis sechs Browser in einem Raum mit gleichzeitigen Bewegungen.
2. Würfelwurf mit mehreren Empfängern, bei langsamer Verbindung und Reconnect.
3. Nicht autorisierte Tokenbewegung, Würfelformeln, Item-Updates und SL-Aktionen blockieren.
4. Zwei Spieler versuchen gleichzeitig dasselbe Item aufzunehmen.
5. Spielleiter hat geheime Gegner; Spieler-Clients erhalten keine Daten darüber.
6. Browser aktualisiert Seite: Positionen, Inventar und letzte Ergebnisse stimmen.
7. Server startet neu: gespeicherte Kampagne bleibt wiederherstellbar.
8. Erstes Deployment auf Test-Linux mit HTTPS, WebSocket und Backup/Restore.
